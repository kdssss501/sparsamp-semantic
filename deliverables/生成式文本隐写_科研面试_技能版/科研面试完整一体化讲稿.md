## Slide 1｜封面：先说明我研究的到底是什么（约 25 秒）

各位老师好，我汇报的项目是《大语言模型生成式文本隐写的可靠编码与跨精度回放研究》。

生成式文本隐写并不是直接把秘密比特替换成字符，而是在语言模型生成每一个 token 时，利用 next-token 概率分布进行受控采样。这样，输出在表面上仍是正常文本，同时可以承载秘密消息；接收端在共享模型、密钥和采样规则的条件下，应当能够恢复消息。

我的项目没有试图把所有现有方法拼成一个新算法，而是聚焦一个更基础的问题：**发送端和接收端真的能在概率采样这一步可靠地做出同一个决定吗？**

【落点】隐写不只是“把信息藏进去”，更关键的是让两端可靠地沿同一条概率轨迹工作。

（切到第 2 页。）

## Slide 2｜问题拆解：可靠性其实有两层（约 45 秒）

我把这里的可靠性拆成两个层次。

第一层是**编码正确性**：发送端停止编码时，接收端能不能恢复原始秘密消息？这是 RRC，也就是 Range Coding 路线最直接的问题。

第二层是**数值回放一致性**：即使双方共享同一个模型、prompt、密钥和随机种子，发送端在 FP16、接收端在 BF16 时，是否仍能选择完全相同的 token 序列？在自回归生成中，只要某一步 token 不同，后续条件概率分布就会全部改变，所以一次很小的数值分歧会放大成整条轨迹失败。

这两层不是同一件事：RRC 处理“消息能否解出”，跨精度回放处理“双方是否还在同一条轨迹上”。但它们有前后依赖关系，因为消息恢复默认双方能重建同一份概率合同。

【落点】算法层解决“能不能解码”，工程层解决“会不会从一开始就走到另一条轨迹”。

（切到第 3 页，给出整体工作线。）

## Slide 3｜项目主线与个人工作：复现、审计、验证（约 45 秒）

围绕这两个层次，我的工作分为三条线。

第一条线是 SparSamp 的兼容复现。我重建了可运行的依赖组合，设计了解码门槛和容量对比矩阵，目的是先得到一个可信的公开基线。

第二条线是 RRC 的可靠编码审计。我把 Algorithm 3 和 Algorithm 4 的区间、旋转和舍入规则写成精确形式，构造了可复现的反例；在此基础上实现了 Verified-RRC 和固定长度认证设计。

第三条线是跨精度回放。我在 Qwen 的 FP16/BF16 设置下先量化共享随机种子为什么不足，再研究怎样只记录真正可能不稳定的采样步骤。这里包含稀疏精度回放证书 SPRC，以及更保守的 BDS，即 Bounded Decision Sets。

请注意，这三条线不是“融合成一个新算法”。它们共享的是对公共概率合同的关注，分别回答基线可否复现、消息可否恢复、轨迹可否回放。

【落点】我的贡献不是把路线硬拼在一起，而是把可靠性拆成可验证的环节。

（切到 SparSamp 基线。）

## Slide 4｜SparSamp：先让公开基线站稳（约 45 秒）

SparSamp 可以理解为：模型给出候选 token 的概率分布，双方用共享密钥生成一致的受控偏移；消息块影响稀疏区间中的采样落点，接收端根据相同规则反向恢复消息。它不是“强行指定某个词”，而是一种可回放的受控采样。

我的定位是兼容复现和比较，而不是宣称提出了 SparSamp 的替代算法。官方 Basic Test 中，我得到 105 个 token、576 bit、5.486 bit/token，并精确解码。随后我运行了 1,200 个配置的兼容矩阵，其中 1,193 个完成；在无 Token Ambiguity 的 846 个完成样本中，全部精确解码。16 项容量对比均在 5% 以内，最大误差为 4.12%。

我也保留了负面结果：FH-SparSamp 的自适应 block 版本在有限 token 预算下成功率下降，所以没有把它包装成改进。

【落点】复现的目的不是重复数字，而是确认后续问题来自可靠性条件，而不是基线失效。

（切到 RRC 原理与审计发现。）

## Slide 5｜RRC：区间缩小不等于消息一定可恢复（约 60 秒）

RRC 的思路是把 l 比特消息视为初始区间 `[0, 2^l)` 中的一个秘密整数。每生成一步，编码器和解码器根据共享偏移旋转这个秘密点，再按 token 概率把当前区间切分为多个子区间；编码器选择包含秘密点的 token 区间。随着区间收缩，原方法使用一个局部停止条件：只要当前区间中点足够接近当前秘密点，就认为接收端可以恢复。

我审计的重点就是这个“认为”。在本项目采用的 Algorithm 3/4 形式化下，接收端不是简单地读出当前中点，而是要逐步进行模逆旋转。模运算有切点，因此圆周上的近距离不能直接当作实数轴上的近距离。

我构造了一个完全使用有理数的两步反例：当 `M=8`、消息 `m=3` 时，原局部停止条件满足，但接收端按照公开 Algorithm 4 反向恢复得到的是 `5`，而不是 `3`。我还构造出一个测度为 `1/1024` 的偏移区域，在这个区域内都会发生同类失败。因此它不是浮点边界上的偶然点。

这里我严格限定结论：在本项目使用的 Algorithm 3/4 形式化下，局部停止条件不是精确恢复的充分条件；这不等于原论文所有结论或实现都错误。

【落点】区间看似缩小到足够近，不等于接收端一定能恢复；真正的判据必须回答“它到底能不能解出来”。

（切到修复方法。）

## Slide 6｜Verified-RRC：把解码结果变成停止判据（约 60 秒）

基于这个发现，我实现了 Verified-RRC。它不改变此前的 token 选择机制：仍然按照原来的区间和偏移规则编码。不同之处只发生在候选停止时刻：编码器先完整模拟一次接收端的公开逆解码，只有确实恢复出原消息时才停止。

因此，Verified-RRC 本质上是一个运行时证书。它不依赖局部几何直觉，而是直接验证接收端的实际输出。

在固定 Mock 概率分布上，我对 16、32、64、128 和 256 bit 的五种 payload，各运行 100 个样本。Verified-RRC 达到 500/500 精确恢复；原局部规则在同一批样本上为 87% 到 96%。验证带来的长度开销很小，平均只增加 0.04 到 0.15 个 token，最多增加 2 个 token。

接下来还有一个信息泄露问题：如果一完成就停止，公开文本长度会暴露内部完成时刻。因此我实现固定长度版本，将 `payload || HMAC 认证标签` 嵌入后继续按同一量化分布采样到公开长度。Mock holdout 中它是 400/400 恢复、0 次错密钥接受。这里的证据仍然是 Mock，不应升级为“真实文本不可检测”或“任意模型一定终止”。

【落点】Verified-RRC 保证的是“成功返回时恢复正确”，不是“对任意模型永远成功”。

（从算法正确性自然过渡到工程正确性。）

## Slide 7｜跨精度回放：10/60 到 60/60 来自哪里（约 65 秒）

到这里，RRC 仍然有一个工程前提：编码器和解码器必须从同一前缀得到相同的概率切分。但在真实推理中，FP16 和 BF16 的舍入、排序或概率分配有微小差异，都可能让某一步选择不同 token。自回归模型一旦分叉，后续 token 便无法通过同一随机种子自动拉回。

这里专门说明 PPT 中最容易混淆的数字。`10/60` 到 `60/60` 来自 R044 的 Qwen 跨精度回放实验，**不是 RRC 的消息恢复实验，也不是 BDS 的独立确认实验**。

具体来说，用 FP16 生成 Qwen2.5-1.5B-Instruct 的参考 token 轨迹，再让 BF16 目标端使用同样的 prompt、公开配置和随机设置回放。未加入修正时，60 条轨迹只有 10 条能全程精确一致。加入 SPRC，也就是面向目标环境构造的稀疏精度回放修正清单后，60 条均精确回放；平均修正率为 2.16%，按 prompt 聚类的 95% 区间为 1.80% 到 2.53%。反向方向 BF16 到 FP16 的受控消融也达到 20/20。

这组结果支持的是：在所测 Qwen 模型、RTX 3060 Laptop GPU 和指定软件栈下，跨精度差异可以被稀疏修正恢复。它不支持跨硬件绝对可复现，也不证明 RRC 的消息恢复率。

【落点】10/60 到 60/60 说的是 token 轨迹回放，不是 RRC 消息恢复。

（切到 BDS，回答“哪些 token 必须修正”。）

## Slide 8｜BDS：用保守决策集解释“为什么可以不记录”（约 65 秒）

R044 说明稀疏修正有效，但还有一个更深的问题：参考端凭什么判定某一步稳定到可以不记录？如果这个判断过于乐观，就可能漏掉真正会分叉的位置。

BDS，也就是 Bounded Decision Sets，处理的就是这个问题。它不是 RRC 的消息编码器，不携带 RRC payload；它是跨精度回放中的保守证书方法。

具体地，BDS 从参考执行的量化 logits 出发，为 token 建立整数区间，并枚举声明的扰动模型内所有可能出现的 top-two 支持、整数概率质量分配和最终采样决定。如果所有可达情况都选择参考 token，那么这个决策集是单例，该步可以不记录；只要可能出现多个 token，就保守地记录参考 token。

它的原则是“宁可多记录，也不把不稳定步骤误判为稳定”。在开发阶段冻结阈值后，R059 用独立 seed 进行确认：在 3,000 个 token 决策上，BDS 实现 40/40 精确回放，未观察到 false-safe，序列化负载为匹配完整轨迹的 54.62%。

作为另一种不同口径的工程基线，R051 的冻结 seed-0 包中，SPRC 是 1,148 B，约为匹配完整 token trace 4,636 B 的 24.76%，也低于 4-token block repair 的 1,408 B。这个 24.76% 是引用式 package 边界，不能和 BDS 的 54.62% 或自包含 JSON 口径直接混用。

【落点】BDS 问的不是“目标端恰好选了什么”，而是“在声明的不确定范围里，它还有没有可能选别的”；不是唯一，就记录。

（切到汇总页，主动划清实验边界。）

## Slide 9｜把结果合在一起，但绝不把数字混在一起（约 45 秒）

到这里，项目的完整逻辑是：SparSamp 先提供可复现的隐写基线；RRC 审计处理消息恢复正确性；SPRC 和 BDS 处理共享概率合同在跨精度环境下是否仍能支撑同一条 token 轨迹。

所以每个数字都必须对应自己的证据。SparSamp 的 `846/846` 是无 Token Ambiguity 子集的兼容复现结果；Verified-RRC 的 `500/500` 是 Mock 下的消息恢复；R044 的 `60/60`、未校正 `10/60` 是跨精度稀疏修正回放；BDS 的 `40/40`、54.62% 是独立 seed 的保守决策证书确认。

它们构成的是前提链，而不是一项端到端结果。当前还没有“将 BDS 直接接入 RRC，并在跨精度两端完成消息隐藏与提取”的联合实验，因此不能写成已经实现的完整系统。

【落点】每个结论都有自己的实验；相关不等于可以合并成一个端到端结论。

## Slide 10｜总结：我的贡献、局限与下一步（约 45 秒）

最后总结三点。

第一，我完成 SparSamp 的兼容复现，建立了可比较的公开基线，也如实保留了自适应 block 的负面结果。

第二，我用精确反例定位了 RRC 局部停止条件的跨边界风险，实现 Verified-RRC，并通过固定长度和 HMAC 认证处理完成时刻泄露的问题。

第三，我在 Qwen FP16/BF16 设置下量化跨精度分歧，验证了稀疏修正回放；进一步用 BDS 为“哪些步骤可以不记录”提供了保守的有限决策证书。

局限同样明确：当前是单模型、单 GPU、指定软件栈的阶段性证据，没有跨硬件验证，没有盲评或检测实验，也没有 BDS-RRC 的端到端联合实验。下一步是让同一整数概率合同同时服务编码器、解码器和回放证书，在独立 GPU 上冻结测试，并同时报告容量、消息恢复、轨迹回放和检测指标。

【结束落点】先把可靠性拆开、逐项验证，再讨论端到端的隐写安全。谢谢各位老师。
