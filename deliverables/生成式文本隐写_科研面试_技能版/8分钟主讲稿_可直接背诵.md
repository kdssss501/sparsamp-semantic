# 8 分钟主讲稿（可直接背诵）

## 1. 题目与问题（25 秒）

各位老师好，我汇报的项目是《大语言模型生成式文本隐写的可靠编码与跨精度回放研究》。生成式隐写利用语言模型的 next-token 概率分布进行受控采样，让文本同时传递自然语言和秘密信息。我的关注点是一个基础前提：发送端和接收端能否在概率采样时可靠地做出同一个决定。

**背诵句：隐写不只是把信息藏进去，更关键的是让两端可靠地沿同一条概率轨迹工作。**

## 2. 两个可靠性问题（40 秒）

我把可靠性分成两层。第一层是消息恢复：编码器结束时，接收端能否恢复原消息？第二层是数值回放：即使模型、prompt、密钥和随机种子相同，FP16 与 BF16 是否还能选出相同 token 序列？前者以 RRC 为对象，后者以 Qwen 跨精度采样为对象。它们相关，但不是同一个实验。

**背诵句：算法层解决能不能解码，工程层解决会不会从一开始就走到另一条轨迹。**

## 3. 我的工作线（35 秒）

围绕这两个问题，我做了三项工作：第一，复现 SparSamp，建立可信基线；第二，审计 RRC 的停止条件，实现 Verified-RRC 和固定长度认证设计；第三，做跨精度回放，量化共享随机种子为何不足，并用稀疏修正和 BDS 验证公共采样决定。

我不把 SparSamp、RRC 和 BDS 说成融合的新算法。它们分别对应基线复现、消息恢复与轨迹回放。

## 4. SparSamp 基线（40 秒）

SparSamp 利用共享密钥产生受控偏移，在稀疏概率结构中让消息块影响采样落点，接收端据此恢复消息。我把它作为兼容复现和比较基线。官方 Basic Test 中，我们得到 105 个 token、576 bit、5.486 bit/token，并精确解码。在 1,200 个配置的矩阵中，1,193 个完成；无 Token Ambiguity 的 846 个完成样本全部精确解码，16 项容量对比均在 5% 误差内。

**背诵句：复现的意义不是重复数字，而是确认后续问题来自可靠性条件，而非基线失效。**

## 5. RRC 审计发现（55 秒）

RRC 将消息表示为初始区间中的秘密整数。每步通过共享偏移旋转秘密点，再按 token 概率切分区间，选择包含秘密点的子区间。原方法认为：最终中点离秘密点足够近时即可停止。

我发现这个局部条件不是精确恢复的充分条件。解码需要做模逆旋转，模运算有切点，圆周上的邻近关系不一定保持为实数轴上的邻近关系。我给出一个精确两步反例：`M=8、m=3` 时局部条件满足，但反向恢复是 `5` 而非 `3`；失败区域的测度为 `1/1024`，并非单个边界点。这个结论只限定在项目采用的 Algorithm 3/4 形式化下。

**背诵句：区间看似缩小到足够近，不等于接收端一定能恢复。**

## 6. Verified-RRC 与固定长度（55 秒）

为此我实现 Verified-RRC：当原规则准备停止时，编码器先完整模拟接收端逆解码，只有恢复出原消息才停止。它不改变此前 token 的选择，而是把“能否解出”变成真正的停止判据。

在固定 Mock 概率分布的 500 个样本中，Verified-RRC 为 500/500 精确恢复；原局部规则是 87% 到 96%，验证平均只多 0.04 到 0.15 个 token。为缓解完成时刻从文本长度泄露的问题，我又做了固定长度版本，将 `payload || HMAC 标签` 嵌入后继续采样到公开长度。它在 Mock holdout 中 400/400 恢复、0 次错密钥接受；这仍不是不可检测性证明。

**背诵句：Verified-RRC 是运行时证书，保证成功返回时正确，不宣称任意模型一定终止。**

## 7. 10/60 与 60/60 的准确含义（60 秒）

上面的 RRC 仍假设双方能重建同一张概率表。实际中，FP16 和 BF16 的微小差异可能让某一步 token 不同；自回归模型一旦分叉，后续概率表也全部改变。

这里专门解释两个数字。`10/60` 到 `60/60` 来自 R044：对 Qwen2.5-1.5B-Instruct，用 FP16 生成参考轨迹，再在 BF16 回放。仅共享随机种子与公开配置时，60 条中只有 10 条全程一致；加入面向目标环境的稀疏 token 修正清单后，60 条都精确回放，平均修正率为 2.16%，95% 区间为 1.80% 到 2.53%。

这说明在指定 Qwen、GPU 和软件栈下，稀疏修正能恢复跨精度 token 轨迹。它不是 RRC 的消息恢复率，也不能外推为跨硬件确定性。

**背诵句：10/60 到 60/60 说的是 token 轨迹回放，不是 RRC 消息恢复。**

## 8. BDS 的角色（60 秒）

R044 说明修正有效，但还要问：参考端如何判断某一步足够稳定、可以不记录？BDS，即 Bounded Decision Sets，给出保守证书。它对量化 logits 建立整数区间，枚举扰动模型内可能出现的 top-two 支持、整数概率合同和采样决定。若所有可达情况都选择参考 token，这一步可以省略；只要可能有多个决定，就记录参考 token。

在冻结阈值后的独立 seed 确认 R059 中，BDS 在 3,000 个 token 决策上实现 40/40 精确回放，未观察到 false-safe，负载为匹配完整轨迹的 54.62%。BDS 不携带 RRC 消息，它补强的是隐写两端共同依赖的公共采样合同。

**背诵句：BDS 的原则是，不是唯一，就记录；宁可多记录，也不把不稳定误判为稳定。**

## 9. 怎样合并这些证据（40 秒）

这些数字不能混用：SparSamp 的 846/846 是兼容复现的无歧义解码证据；Verified-RRC 的 500/500 是 Mock 消息恢复；R044 的 60/60 是跨精度稀疏修正回放；BDS 的 40/40 是独立 seed 的保守证书确认。

它们是一条前提链，而不是一项端到端实验。当前没有把 BDS 直接接入 RRC，并在跨精度两端完成隐藏与提取的联合实验证据。

## 10. 总结与下一步（40 秒）

总结来说，我完成了 SparSamp 兼容复现；用精确反例定位 RRC 的停止正确性缺口，并实现 Verified-RRC 与固定长度认证设计；又在 Qwen FP16/BF16 条件下验证了稀疏修正回放和 BDS 保守证书。

局限是单模型、单 GPU、没有跨硬件、没有盲评或检测实验，也没有 BDS-RRC 端到端联合实验。下一步是把同一整数概率合同接入编码器和解码器，在独立 GPU 上冻结测试，同时报告容量、消息恢复、轨迹回放和检测指标。谢谢各位老师。

**结束背诵句：先把可靠性拆开、逐项验证，再讨论端到端的隐写安全。**

## 一页口径卡

- `10/60 -> 60/60`：R044，FP16 到 BF16 的 Qwen token 轨迹回放，使用稀疏目标特定修正。
- `40/40, 54.62%`：R059，BDS 独立 seed 确认。
- `500/500`：R012，Mock 下的 Verified-RRC 消息恢复。
- `400/400, 0 次错密钥接受`：R020，Mock 下的 Fixed-Length RRC。
- 不说：已发表、零 KL、完全不可检测、通用安全、跨硬件绝对可复现、BDS-RRC 已端到端融合。
