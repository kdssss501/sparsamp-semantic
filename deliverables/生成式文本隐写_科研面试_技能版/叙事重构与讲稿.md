# 科研面试叙事重构：把“隐写项目”讲成一条清晰的线

## 0. 先把项目边界说清楚

本项目不是把 SparSamp、RRC 和 BDS 融合成一个新算法，而是围绕“概率采样两端怎样可靠一致”做了三项相互支撑、但实验上彼此独立的工作：

1. **SparSamp 兼容复现**：确认生成式文本隐写的公开基线可运行、可比较。
2. **RRC 可靠编码审计**：研究“发送端嵌入的消息，接收端能否正确恢复”。
3. **跨精度轨迹回放**：研究“即使共享模型、密钥和随机种子，两端的采样 token 是否仍能一致”。R044 的 10/60 与 60/60 属于这一条；BDS 的 40/40 是这一条上的保守证书方法确认，**不是 RRC 的消息恢复实验**。

一句总述：**我把生成式文本隐写中常被默认成立的“两端一致性”，拆成了消息恢复正确性和数值回放一致性两个可验证问题，并分别给出证据与边界。**

## 1. 面试开场：先给老师一张“问题地图”（约 45 秒）

### 页面要点

- 大语言模型隐写：在每一步 next-token 概率分布中编码消息。
- 前提：发送端和接收端要基于同一条概率采样轨迹做出一致决定。
- 可靠性有两层：**消息能否解出**，以及**token 轨迹能否重放**。
- 项目不宣称一个融合算法，而是分别审计与验证两层。

### 完整讲述

各位老师好，我汇报的项目是《大语言模型生成式文本隐写的可靠编码与跨精度回放研究》。

生成式文本隐写的基本想法是：语言模型每生成一个 token，都会给出一张概率表。发送端不直接把秘密比特写进文本，而是利用概率表进行受控采样，让生成的文本同时承担自然语言和信息传递两种功能。接收端只要拥有相同的模型、密钥和采样规则，就应当沿着相同轨迹恢复消息。

但这里有一个经常被忽略的前提：两端必须真的“算出同一个决定”。因此我把可靠性拆成两个问题。第一，编码器停止时，接收端能否精确恢复秘密消息？第二，即使共享随机种子，发送端在 FP16、接收端在 BF16 时，能否重放同一条 token 轨迹？项目的工作就是分别处理这两个问题。

### 背诵句

> **隐写的核心不只是“把信息藏进去”，而是让两端在概率采样这一步可靠地达成同一个决定。**

## 2. 项目主线与个人工作：从复现到审计，再到工程验证（约 50 秒）

### 页面要点

| 工作线 | 回答的问题 | 我的具体工作 | 证据 |
|---|---|---|---|
| SparSamp | 公开基线是否可复现？ | 重建兼容环境、矩阵实验、解码与容量核验 | R001/R002 |
| RRC | 局部停止后能否保证消息恢复？ | 精确反例、Verified-RRC、固定长度认证帧 | R012/R020 |
| 回放与 BDS | 跨精度时 token 轨迹能否保持一致？ | FP16/BF16 实验、稀疏修正与 BDS 决策集验证 | R044/R059 |

### 完整讲述

我的工作不是从零提出一个包打天下的新隐写算法，而是沿着一条更可验证的路线推进。

第一步，我复现 SparSamp 作为公开基线，确认实验环境、解码门槛和容量趋势都可检查。第二步，我对 RRC 的编码和解码规则做形式化审计，发现局部停止条件不能单独保证消息恢复，并把检查直接放进编码过程，得到 Verified-RRC。第三步，我转向工程层面：即使算法逻辑正确，FP16 和 BF16 的微小差异也会造成 token 分叉，所以我做了稀疏修正回放和 BDS 的保守决策证书。

这三项工作的共同点是“概率合同必须被验证”；不同点是，RRC 验证的是消息是否恢复，BDS 验证的是公共采样决定是否稳定。

### 背诵句

> **我的贡献不是把不同路线硬拼在一起，而是把可靠性拆开：算法层检查能否解码，工程层检查能否复放。**

## 3. SparSamp：为什么先做复现（约 40 秒）

### 页面要点

- SparSamp 是复现与比较基线，不是本项目提出的新算法。
- Basic Test：105 tokens、576 bits、5.486 bit/token、精确解码。
- R002：1,193/1,200 配置完成；无 Token Ambiguity 子集 846/846 精确解码。
- 16/16 容量对比在 5% 内，最大误差 4.12%。

### 完整讲述

在进入方法改进之前，我先做了 SparSamp 的兼容复现。它的思想是利用共享密钥产生受控偏移，再在稀疏概率结构中让消息块决定采样落点。接收端根据相同概率合同反向恢复消息。

我把这一步定位为基线复现，而不是宣称新方法。官方 Basic Test 中，我们得到 105 个 token、576 bit、5.486 bit/token，并且精确解码。随后在 1,200 个配置的矩阵中，1,193 个完成；在无 Token Ambiguity 的 846 个完成样本中全部精确解码，16 项容量对比都落在 5% 误差内。

这些结果的意义是建立一个可信起点：后续看到的问题，不是来自“基线根本跑不起来”，而是来自可靠性条件本身。

### 背诵句

> **复现不是为了重复一个数字，而是为了把后续结论建立在可核验的公共基线上。**

## 4. RRC：第一个可靠性问题是“消息能否解出来”（约 55 秒）

### 页面要点

- 将消息整数映射为初始区间中的秘密点。
- 每步：共享偏移旋转秘密点，按 token 概率切分区间，选择所在子区间。
- 原局部停止条件只检查最终中点靠近秘密点。
- 关键风险：反向模旋转存在切点，局部线性距离不一定能回传到初始消息。

### 完整讲述

RRC 是第二条隐写路线。它把 l 比特消息看作区间 `[0, 2^l)` 中的一个秘密整数。每一步，双方利用共享偏移旋转这个秘密点，再用 token 概率把当前区间切分；编码器选取包含秘密点的 token 区间。区间持续收缩，直到认为当前信息已经足够恢复。

我审计的重点不是 RRC 的采样思想，而是它的停止逻辑。原规则只检查最终区间中点和当前秘密点距离是否落在半个单位内。直觉上似乎足够，但解码器会把这个中点依次做模逆旋转。模运算有切点，圆周上的邻近关系并不等于实数轴上的邻近关系，所以局部的半单位误差会在反向过程中跨边界放大。

### 背诵句

> **RRC 的问题不在于区间会不会缩小，而在于“缩小到看似足够”是否真的等价于“接收端能够恢复”。**

## 5. 关键发现与修复：Verified-RRC 和固定长度（约 60 秒）

### 页面要点

- 精确反例：`M=8, m=3`，局部条件满足，反向恢复为 `5 != 3`。
- 失败并非零测度巧合：构造的偏移区域测度为 `1/1024`。
- Verified-RRC：候选停止时完整执行一次公开逆解码；只有恢复原消息才停止。
- R012 Mock：500/500 精确恢复；原局部规则为 87%–96%；平均额外 0.04–0.15 token。

### 完整讲述

我给出了一个完全使用有理数的两步反例：当 `M=8`、消息 `m=3` 时，原局部停止条件满足，但接收端按公开逆过程恢复得到的是 5，而不是 3。更重要的是，我进一步构造出测度为 `1/1024` 的连续偏移区域，所以它不是某个浮点边界上的偶然点。

基于这个发现，我实现 Verified-RRC。它不改变前面的 token 选择机制，只是在原规则准备停止时，先完整模拟接收端的逆解码；只有确认能得到原消息时才输出。因此它是一个运行时正确性证书。

在固定的 Mock 概率分布下，五种 payload 长度、共 500 个样本全部精确恢复；原局部规则的恢复率是 87% 到 96%，而验证只带来平均 0.04 到 0.15 个 token 的增加。

进一步地，立即停止会让公开文本长度暴露内部完成时刻。因此我实现固定长度版本：将 `payload || HMAC 标签` 嵌入，完成后继续按同一分布采样到公开长度。Mock holdout 是 400/400 恢复、0 次错密钥接受，但它仍只是 Mock 证据，不能称为不可检测性证明。

### 背诵句

> **Verified-RRC 的思想很朴素：不再用局部几何直觉替代解码，而是把“接收端能否解出”作为真正的停止判据。**

## 6. 从消息恢复转到数值回放：这是一条独立问题线（约 45 秒）

### 页面要点

- RRC 假设双方能重建相同概率切分；实际硬件/精度可能不满足。
- 同一模型、prompt、随机种子，FP16 与 BF16 仍可能在某一步选到不同 token。
- 自回归放大：一个 token 分叉后，后续条件分布也改变。
- 因此需要单独验证跨精度 token 回放。

### 完整讲述

到这里可以看出，Verified-RRC 仍依赖一个前提：编码器和解码器对同一前缀得到相同的概率切分。但真实推理中，这个前提会被数值精度破坏。FP16 和 BF16 的舍入、排序或概率分配只要有很小差异，就可能在某一步采到不同 token；而语言模型是自回归的，一次分叉以后，两边看到的下一步概率表也不同。

所以跨精度回放不是 RRC 的直接实验结果，而是它赖以运行的底层工程条件。我把它作为独立工作线处理：先测量共享随机种子到底够不够，再研究怎样只记录真正不稳定的决定。

### 背诵句

> **消息恢复解决“解码器会不会算错”，跨精度回放解决“解码器会不会从一开始就走到另一条轨迹上”。**

## 7. R044：10/60 和 60/60 到底说明什么（约 55 秒）

### 页面要点

- 对象：Qwen2.5-1.5B-Instruct 的 FP16 参考轨迹与 BF16 目标回放。
- 未校正的 shared-seed 控制组：10/60 精确回放。
- 加入稀疏的目标特定修正清单后：60/60 精确回放。
- 平均修正率 2.16%，prompt-cluster 95% CI `[1.80%, 2.53%]`。
- 这组实验是 **SPRC/稀疏修正回放**，不是 RRC 消息解码，也不是 BDS 的 R059 确认集。

### 完整讲述

这里专门解释 PPT 中最容易被误读的两个数字。`10/60` 和 `60/60` 来自 R044，不是 RRC 实验，也不是 BDS 的独立确认实验。

R044 的对象是 Qwen2.5-1.5B-Instruct：用 FP16 产生一条参考 token 轨迹，再尝试在 BF16 中用同样的公开随机设置重放。若只共享随机种子和公开配置，不加修正，60 条轨迹中只有 10 条完整一致。加入稀疏的、面向这个目标环境构造的 token 修正清单后，60 条都精确一致，平均只有 2.16% 的位置需要修正，按 prompt 聚类的 95% 区间是 1.80% 到 2.53%。

这个结果支持的是：在所测 Qwen、GPU 和软件栈下，跨精度分歧并非每一步都发生，稀疏修正可以恢复参考轨迹。它不能支持跨硬件绝对复现，也不能证明 RRC 的消息恢复。

### 背诵句

> **10/60 到 60/60 证明的是“稀疏修正能恢复 Qwen 的跨精度 token 轨迹”，不是“RRC 的消息恢复率从 10/60 提升到 60/60”。**

## 8. BDS：让“哪些步骤可省略”有保守的理由（约 60 秒）

### 页面要点

- BDS = Bounded Decision Sets，独立于 RRC 的跨精度回放证书方法。
- 对参考 logits 给出量化整数区间，枚举所有可能的 top-two 支持与整数质量分配。
- 决策集只有一个 token：该步可以不记录；存在多个可能 token：保守记录参考 token。
- R059 独立 seed：40/40 精确回放、3,000 个 token 决策、0 observed false-safe、负载为完整轨迹的 54.62%。

### 完整讲述

R044 说明稀疏修正有效，但还留下一个问题：发送端凭什么认定某一步“稳定到可以不记”？BDS，也就是 Bounded Decision Sets，处理的是这个问题。

它不携带 RRC 的秘密消息，也不做 RRC 解码。它从参考执行的量化 logits 出发，为每个 token 给出允许的整数区间，枚举在这个扰动模型内所有可能出现的 top-two 支持、整数概率合同和最终采样决定。如果所有可达情况都只会选出参考 token，这一步就得到一个单例决策集，可以安全省略；只要可能出现多个决定，就保守地把参考 token 记录下来。

因此 BDS 的设计方向是“宁可多记录，也不把不稳定步骤误判成稳定”。在冻结阈值后、独立 seed 的 R059 中，它在 3,000 个 token 决策上完成 40/40 精确回放，未观察到 false-safe；序列化负载是匹配完整轨迹的 54.62%。这说明有限整数扰动模型下的保守证书有可行性，但证据仍限于一个 Qwen 模型、一个 RTX 3060 Laptop GPU 与指定软件栈。

### 背诵句

> **BDS 不问“目标端这一步恰好选了什么”，而是问“在声明的数值不确定范围内，它还有没有可能选别的”。只要答案不是唯一，就记录。**

## 9. 结果如何合并理解：不是一个数字证明全部（约 50 秒）

### 页面要点

| 结论 | 正确证据 | 不能外推为 |
|---|---|---|
| SparSamp 可兼容复现 | R002：846/846 无歧义精确解码 | 严格原依赖环境复现 |
| Verified-RRC 成功时正确 | 精确反例 + R012 500/500 Mock | 任意模型必然终止 |
| 稀疏修正可跨精度回放 | R044：60/60，未校正 10/60 | 跨硬件确定性 |
| BDS 可保守筛出待记录步骤 | R059：40/40，0 observed false-safe | 通用浮点误差证明 |

### 完整讲述

最后把证据合在一起时，最重要的是不让一个结果替代另一个结果。SparSamp 的数据说明兼容复现基线成立；RRC 的反例和 Verified-RRC 说明停止时的消息恢复应该被显式验证；R044 说明在 Qwen 的 FP16/BF16 测试中，少量修正足以恢复轨迹；R059 则说明 BDS 在声明的整数扰动范围内，能以保守方式筛出必须记录的步骤。

它们之间的关系是前提链，而不是同一实验的四个指标：可靠消息恢复需要两端同步概率合同，而 BDS 与稀疏修正是在补强这个同步前提。当前还没有“把 BDS 直接嵌入 RRC，并在跨精度两端完成端到端消息隐藏和提取”的联合实验；这是下一步要做的验证，而不能提前写成已经完成的贡献。

### 背诵句

> **我把每个结论都对应到自己的实验：消息恢复看 RRC，轨迹一致看 R044/BDS，二者相关，但目前不混作一项端到端结果。**

## 10. 收束：贡献、局限与下一步（约 45 秒）

### 页面要点

- 贡献 1：完成 SparSamp 兼容复现并保留负面结果。
- 贡献 2：给出 RRC 停止规则跨边界反例，实现 Verified-RRC 与固定长度认证设计。
- 贡献 3：用 R044 与 BDS/R059 分别验证跨精度稀疏修正和保守决策证书。
- 局限：单模型、单 GPU；无跨硬件；无盲评/检测；无 BDS-RRC 端到端联合实验。
- 下一步：以同一整数概率合同把 BDS 接入编码器/解码器，做跨 GPU 的冻结传输实验，并报告容量、恢复率和检测指标。

### 完整讲述

总结一下，我的项目贡献主要有三层：首先完成了 SparSamp 的兼容复现，建立可比较基线；其次在 RRC 中用精确反例定位局部停止条件的跨边界风险，并实现成功时可验证恢复的 Verified-RRC 和固定长度认证设计；最后在工程层面量化跨精度分歧，通过 R044 和 BDS 分别验证稀疏修正回放与保守决策证书。

局限也必须明确：当前证据覆盖的是指定 Qwen、单 GPU 和指定软件栈，没有跨硬件实验，没有真人盲评或检测实验，也没有 BDS 与 RRC 的端到端联合实验。因此下一步最关键的工作，是把 BDS 的整数概率合同接入同一个编码/解码器，并冻结参数后迁移到独立 GPU，分别报告消息恢复、轨迹回放、容量和检测结果。

现阶段，我更愿意把项目定义为一套可审计的可靠性研究，而不是宣称已经完成了通用安全的隐写系统。谢谢各位老师。

### 结束背诵句

> **我的结论始终带着条件：先把可靠性拆开、逐项验证，再讨论端到端的隐写安全。**
