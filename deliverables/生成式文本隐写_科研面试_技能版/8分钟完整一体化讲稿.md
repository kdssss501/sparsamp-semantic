# 科研面试完整一体化讲稿（10 页，约 8 分钟）

> 正文可以直接连续讲。每页最后的“落点”用于自然切页，不必额外解释。全稿约 2,500 个中文字符，按每分钟约 320 字的面试语速控制在 8 分钟内。

## Slide 1｜开场（25 秒）

各位老师好，我汇报的项目是《大语言模型生成式文本隐写的可靠编码与跨精度回放研究》。生成式文本隐写是在语言模型每一步的 next-token 概率分布中进行受控采样，使输出文本在保持自然语言形式的同时承载秘密信息。我的核心关注点是：发送端和接收端能否可靠地在概率采样这一步做出同一个决定。

**落点：隐写不仅要能嵌入信息，更要让两端走在同一条概率轨迹上。**

## Slide 2｜两个可靠性问题（40 秒）

我把可靠性拆成两层。第一层是消息恢复：编码器停止时，接收端能不能恢复原消息？第二层是数值回放：即使模型、prompt、密钥和随机种子相同，FP16 和 BF16 是否还能选出同一条 token 序列？自回归生成中，一个 token 分叉会改变后续所有条件分布，所以很小的数值差异也可能造成整条轨迹失败。

前者对应 RRC 的编码和解码正确性，后者对应 Qwen 的跨精度采样回放。两者相关，但不能把它们当作同一个实验。

**落点：算法层解决能不能解码，工程层解决会不会从一开始就走到另一条轨迹。**

## Slide 3｜我的工作线（40 秒）

围绕这个问题，我完成三项工作。第一，复现 SparSamp，建立公开基线；第二，审计 RRC 的停止条件，给出精确反例并实现 Verified-RRC 与固定长度认证设计；第三，在 Qwen 的 FP16/BF16 条件下研究跨精度回放，用稀疏修正和 BDS 检查公共采样决定。

因此 SparSamp、RRC 和 BDS 不是融合后的新算法。它们分别服务于基线复现、消息恢复和轨迹回放，三者共同指向“概率合同是否可靠”。

## Slide 4｜SparSamp：建立可信基线（40 秒）

SparSamp 使用共享密钥产生受控偏移，在稀疏概率结构中让消息块影响采样落点，接收端再按相同规则恢复消息。我把它定位为兼容复现和比较对象。

官方 Basic Test 中，我得到 105 个 token、576 bit、5.486 bit/token，并精确解码。在 1,200 个配置的兼容矩阵中，1,193 个完成；无 Token Ambiguity 的 846 个完成样本全部精确解码，16 项容量对比都在 5% 误差内，最大误差为 4.12%。这说明后续讨论建立在可核验的基线上。

**落点：复现的目的不是重复数字，而是确认后续问题来自可靠性条件，而非基线失效。**

## Slide 5｜RRC：发现“局部停止”存在缺口（55 秒）

RRC 把消息表示为初始区间中的秘密整数。每一步利用共享偏移旋转秘密点，再按 token 概率切分区间，选择包含秘密点的子区间。原方法认为，当最终中点足够接近秘密点时即可停止。

我审计后发现，在项目采用的 Algorithm 3/4 形式化下，这个局部条件不是精确恢复的充分条件。原因是解码要逐步做模逆旋转，模运算有切点，圆周上的近距离不一定保持为实数轴上的近距离。

我给出完全使用有理数的两步反例：`M=8、m=3` 时局部条件满足，但反向恢复是 `5` 而不是 `3`；并且失败区域测度为 `1/1024`，不是单个边界点。这个结论不等于原论文所有内容都错误，只说明局部停止条件不能替代实际解码验证。

**落点：区间看似已经足够近，不等于接收端一定能恢复。**

## Slide 6｜Verified-RRC：把“能不能解出”变成判据（55 秒）

因此我实现 Verified-RRC。它不改变此前 token 的选择；只在候选停止时完整模拟接收端的公开逆解码，只有恢复原消息才停止。这本质上是一个运行时正确性证书。

在五种 payload 长度、共 500 个固定 Mock 样本中，Verified-RRC 达到 500/500 精确恢复；原局部规则在同一批样本中为 87% 到 96%，而验证平均只增加 0.04 到 0.15 个 token。针对完成时刻可能从文本长度泄露的问题，我又实现固定长度版本：嵌入 `payload || HMAC 标签` 后继续采样到公开长度。Mock holdout 为 400/400 恢复、0 次错密钥接受。

这些结果说明成功时可验证恢复正确，但仍是 Mock 证据，不宣称任意模型必然终止或真实文本不可检测。

**落点：Verified-RRC 保证成功返回时正确，而不是承诺所有场景都必然成功。**

## Slide 7｜跨精度回放：10/60 与 60/60 的准确来源（65 秒）

RRC 仍有一个工程前提：双方必须重建同一张概率表。FP16 与 BF16 的微小舍入、排序或概率分配差异，都可能让某一步 token 不同；一旦分叉，后续轨迹无法只靠同一随机种子自动拉回。

这里需要特别说明，`10/60` 到 `60/60` 来自 R044 的 Qwen 跨精度回放，不是 RRC 的消息恢复实验，也不是 BDS 的确认实验。具体做法是：用 FP16 生成 Qwen2.5-1.5B-Instruct 的参考轨迹，再在 BF16 目标端按同样公开设置回放。未加入修正时，60 条中只有 10 条全程一致；加入面向目标环境的稀疏精度回放修正清单 SPRC 后，60 条均精确回放，平均修正率为 2.16%，95% 区间为 1.80% 到 2.53%。反向 BF16 到 FP16 的受控消融也达到 20/20。

这支持的是指定模型、GPU 和软件栈下的跨精度回放，不是跨硬件确定性。

**落点：10/60 到 60/60 说的是 token 轨迹回放，不是 RRC 的消息恢复率。**

## Slide 8｜BDS：保守地判断哪些步骤必须记录（65 秒）

R044 说明稀疏修正有效，但还要回答：参考端如何判定某一步稳定到可以不记录？BDS，也就是 Bounded Decision Sets，处理的是这个保守证书问题。

BDS 从参考执行的量化 logits 出发，为 token 建立整数区间，枚举声明的不确定范围内可能出现的 top-two 支持、整数概率合同和采样决定。如果所有可达情况都选参考 token，就省略；只要存在多个可能 token，就记录参考 token。它的原则是宁可多记录，也不把不稳定步骤错判为稳定。

在冻结阈值后的独立 seed 确认 R059 中，BDS 在 3,000 个 token 决策上实现 40/40 精确回放，未观察到 false-safe，负载为匹配完整轨迹的 54.62%。BDS 不携带 RRC 消息，它补强的是隐写双方共同依赖的公共采样合同。

**落点：不是唯一，就记录；BDS 用保守性换取回放可靠性。**

## Slide 9｜怎样合并结果（40 秒）

到这里，项目的逻辑是一条前提链：SparSamp 提供可复现基线；RRC 审计消息恢复正确性；SPRC 和 BDS 处理跨精度时公共概率合同能否维持同一 token 轨迹。

数字必须各归其位：`846/846` 是 SparSamp 无歧义子集的兼容复现；`500/500` 是 Mock Verified-RRC 恢复；R044 的未校正 `10/60`、校正后 `60/60` 是稀疏修正回放；BDS 的 `40/40` 和 54.62% 是独立 seed 的保守证书确认。

当前还没有把 BDS 直接接入 RRC，在跨精度两端完成消息隐藏和提取的联合实验，不能提前把它说成端到端系统。

**落点：每个结论对应自己的实验，相关不等于可以混成一个端到端结果。**

## Slide 10｜总结与未来（45 秒）

总结来说，我完成了 SparSamp 兼容复现；用精确反例定位 RRC 停止正确性的跨边界风险，并实现 Verified-RRC 与固定长度认证设计；又在 Qwen FP16/BF16 条件下验证稀疏修正回放，并用 BDS 为稳定采样决定提供保守证书。

当前局限是单模型、单 GPU、指定软件栈，没有跨硬件、盲评或检测实验，也没有 BDS-RRC 的端到端联合实验。下一步是让同一整数概率合同同时服务编码器、解码器和回放证书，在独立 GPU 上冻结测试，同时报告容量、消息恢复、轨迹回放与检测指标。

**结束落点：先把可靠性拆开、逐项验证，再讨论端到端的隐写安全。谢谢各位老师。**
