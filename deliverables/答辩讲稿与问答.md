# 《大语言模型生成式文本隐写的可靠编码与跨精度回放研究》

## 使用方式

整场汇报控制在 8 分钟。每页不需要逐字照读，先记住每页的第一句和最后一句即可。所有数据结论都带有范围限定，避免被老师追问时出现过度表述。

## 逐页讲稿

### 1. 标题页（25 秒）

各位老师好，我汇报的项目是“大语言模型生成式文本隐写的可靠编码与跨精度回放研究”。项目关心的不只是把消息嵌入文本，更关注接收端能否正确恢复，以及模型在不同数值精度下能否稳定重放相同 token 序列。

### 2. 研究背景（45 秒）

大语言模型在每一步都会给候选 token 分配概率。生成式文本隐写利用这张概率表，在看起来正常的生成过程中编码秘密比特。接收端只要拥有相同的密钥、模型和配置，就应能反向恢复消息。难点是它同时受到文本自然性、容量、恢复正确性和可检测性的约束。

### 3. 问题定义（45 秒）

这四个目标并不是天然一致的。高容量可能影响文本质量；逐步匹配 token 分布，也不自动证明变长全文分布匹配。本项目的贡献重点是可靠恢复、停止长度泄露缓解和数值回放一致性，而不是宣称已解决全部安全问题。

### 4. 两条路线（40 秒）

项目复现、比较了 SparSamp 和 RRC 两条路线。SparSamp 是在候选 token 概率分布上的受控稀疏采样；RRC 是把秘密消息映射到概率区间，按 token 概率不断收缩区间。我没有把它们称为融合算法，而是以 RRC 为主要可靠性审计对象。

### 5. SparSamp（55 秒）

SparSamp 可以理解成：模型给出候选词及概率，双方用密钥得到一致的受控偏移，消息块决定在这个候选空间中如何选择。关键不在于强行指定一个词，而是在模型原有概率分布上进行可回放的采样。这一部分在项目中主要承担复现和对比作用。

### 6. RRC（55 秒）

RRC 把 l 比特消息看成初始区间中的一个秘密点。每一步用共享偏移旋转该点，再按当前语言模型的 token 概率把区间分割，选择包含秘密点的子区间并输出对应 token。接收端用相同前缀、偏移和分割规则逆向重放，目标是恢复原消息。

### 7. 关键发现（60 秒）

我审计 RRC 的停止逻辑时发现，在项目采用的 Algorithm 3/4 形式化下，局部中点足够接近当前秘密点，并不是精确恢复的充分条件。原因是逆旋转存在切点，跨过切点后数轴上的局部距离不能直接保持。项目给出了一个两步精确有理数反例，最终会得到 `round(19/4)=5`，而原消息是 3。这里的表述边界是：不能据此说原论文所有实现都错误。

### 8. 方法改进（55 秒）

因此我实现了 Verified-RRC：当局部规则满足时，不立即停止，而是完整模拟接收端逆重放；只有确实能恢复原消息才接受停止。R012 的 Mock 审计中，原局部规则恢复率为 87% 到 96%，Verified-RRC 是 500/500 精确恢复，平均只增加 0.04 到 0.15 个 token。固定长度版本把消息与 HMAC 标签一起嵌入，并采样到公开长度 N，以缓解停止长度泄露。它不是任意模型必然终止的证明。

### 9. BDS（55 秒）

在工程上，FP16 和 BF16 的微小 logit 差异可能使一个 token 不同，并在后续自回归生成中放大。BDS 建立公开整数概率合同，并判定某一步在允许的数值不确定范围内是否一定选同一 token。一定稳定的步骤不记录，不稳定的步骤记录修正信息。R059 的独立 seed 中有 40/40 精确回放、观测到 0 次 false-safe，但只适用于 Qwen2.5-1.5B、RTX 3060 Laptop 和指定软件栈。

### 10. 结果与总结（70 秒）

我把工作总结为三点：第一，复现比较两条生成式文本隐写路线；第二，通过精确反例审计 RRC 停止正确性，实现 Verified-RRC 和固定长度认证设计；第三，设计 BDS 应对跨精度离散决策分叉。在指定实验中，校正后有 60/60 精确 token 回放，未校正为 10/60。当前成果是 working paper 和项目阶段成果，不是已发表论文，也不代表通用安全、完全不可检测或跨硬件保证。后续会扩大模型和硬件矩阵，并补充文本质量和检测实验。

## 高频追问与稳妥回答

### 1. SparSamp 和 RRC 是不是被你融合了？

不是。它们是两条独立路线。项目做的是复现、比较并在 RRC 路线上扩展可靠恢复、固定长度认证和跨精度回放机制。除非后续有真实联合算法和完整实验，我不会称为融合。

### 2. 为什么局部停止条件会失败？

局部条件只在当前区间看中点与秘密点的距离，但逆旋转是模区间映射，存在切点。跨越切点后，表面上很小的误差可能在反向映射时多出一个区间宽度，最终落到错误的舍入单元。Verified-RRC 通过完整逆重放直接验证，避免只依赖局部判据。

### 3. HMAC 在固定长度 RRC 中做什么？

嵌入帧是 `F = m || HMAC(K_auth, domain || l || context || m)[:a]`。接收端扫描各个前缀，只有 HMAC 验证通过才接受候选消息。它主要防止错误前缀被误当成消息，并让接收端不需要公开真实完成时刻。默认 128 bit 标签；教学中的短标签不能用于真实安全结论。

### 4. BDS 为什么不能直接说跨硬件可复现？

BDS 的精确性需要一个已声明的模型、tokenizer、采样配置和目标数值环境。项目 R059 只在指定 Qwen、RTX 3060 Laptop 和软件栈中做了独立 seed 确认。不同 GPU、驱动、算子或 tokenizer 都可能扩大决策不确定性，因此需要独立实验验证。

### 5. 这个项目的创新点和局限分别是什么？

创新更准确地说是可靠性审计和工程扩展：构造 RRC 局部终止的精确反例，实现逆重放验证、固定长度认证，并将跨精度分叉变成可审计的稀疏修正问题。局限是样本和环境有限，尚未给出任意模型的有限终止证明，也没有现实世界不可检测或通用跨硬件的证明。

## 真实性检查清单

- 可以说：复现、比较并扩展 SparSamp 与 RRC 两条路线。
- 可以说：R012 Mock 审计中 Verified-RRC 为 500/500 精确恢复；必须同时说明是 MockProvider 条件。
- 可以说：R059 独立 seed 合计 40/40 精确回放、0 observed false-safe；必须同时说明模型和硬件范围。
- 不可以说：融合 SparSamp 与 RRC 为新算法。
- 不可以说：论文已发表或已投稿。当前材料为 working paper / 项目阶段成果。
- 不可以说：零 KL、完全不可检测、通用安全或跨硬件绝对可复现。
- 不可以说：RRC 原论文所有实现错误。正确说法是：在项目采用的 Algorithm 3/4 形式化下，局部停止条件不是精确恢复的充分条件。
